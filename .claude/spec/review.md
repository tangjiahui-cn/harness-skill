### 0.2 交付物 1：`references/review-spec.md`

**用途**：Spec 规格文档审查专用。审查对象是 `.harness/temp/{vId}/spec.md`。

**必须包含以下内容**：

#### ① P0/P1/P2 分类表（文档导向）

| 等级 | 类别 | 描述 |
|------|------|------|
| 🔴 P0 | 内容遗漏 | 关键的功能规格、边界条件、异常流程缺失，导致开发无法正常推进 |
| 🔴 P0 | 逻辑矛盾 | 同一 spec 中存在相互冲突的功能描述、技术选型或数据定义 |
| 🔴 P0 | 方案缺陷 | 技术方案明显不可行、选型错误，会导致后续工作走错方向 |
| 🔴 P0 | 不可验证 | 验收标准缺失或模糊，开发完成后无法判断是否达标 |
| 🟡 P1 | 描述不清 | 表述含糊、有歧义，多个读者可能产生不同理解 |
| 🟡 P1 | 边界缺失 | 输入校验、空状态、并发、超时等边界条件未覆盖 |
| 🟡 P1 | 上下文断裂 | 依赖外部系统或前置假设但不做说明，读者无法理解上下文 |
| 🟡 P1 | 不完整 | 某部分有改进空间，但当前版本尚可工作 |
| 🟢 P2 | 措辞润色 | 表述可更精炼或清晰，但不影响理解 |
| 🟢 P2 | 格式风格 | 排版、标记风格不一致 |
| 🟢 P2 | 过度设计 | 为不确定的未来做的提前扩展 |

> 分类表直接沿用通用文档框架，与 common_review.md 保持一致。

#### ② 检查重点清单

- 功能规格是否完整覆盖用户需求
- 技术方案是否可行且合理（选型理由、替代方案对比）
- 边界条件和异常场景是否覆盖（输入校验、空值、网络超时、并发冲突）
- 非功能需求是否明确（性能指标、安全要求、兼容性）
- 验收标准是否可验证（不应出现"系统应流畅运行"这类模糊表述）
- 涉及的文件结构是否完整列出

#### ③ "无问题"判断标准

父 Agent 判断 spec 可以退出循环的标准：

- P0 列表为空（无遗漏、无矛盾、方案可行、验收标准可衡量）
- P1 列表中无"内容缺失"类的实质性问题，仅含措辞或格式建议

#### ④ 建议文件命名

- 建议文件：`spec-suggest.md`
- 输出目录：`.harness/temp/{vId}/`

### 0.3 交付物 2：`references/review-plan.md`

**用途**：Plan 执行计划审查专用。审查对象是 `.harness/temp/{vId}/plan.md`。

**必须包含以下内容**：

#### ① P0/P1/P2 分类表（流程导向）

| 等级 | 类别 | 描述 |
|------|------|------|
| 🔴 P0 | 步骤遗漏 | 必要的开发步骤缺失（如漏掉数据库迁移、配置变更、数据迁移脚本），导致执行不完整 |
| 🔴 P0 | 依赖错误 | 步骤间依赖关系不合理（如 Step 3 使用 Step 5 才创建的文件，或多个步骤交叉修改同一文件但未声明先后顺序） |
| 🔴 P0 | 逻辑矛盾 | 同一 plan 中出现冲突的描述，如验收标准与步骤目标不一致，或步骤顺序违反技术常识 |
| 🔴 P0 | 不可验证 | 某步骤的验收标准缺失或模糊，执行 Agent 完成后无法自检是否合格 |
| 🟡 P1 | 描述不清 | 步骤目标或操作描述含糊，执行 Agent 不知道该做到什么程度 |
| 🟡 P1 | 粒度不当 | 步骤划分不合理——单个步骤过大（包含多个独立逻辑）或过小（大量单文件步骤，导致不必要的提交） |
| 🟡 P1 | 文件遗漏 | 某步骤涉及的文件未在"涉及文件"中列出，影响 allowedPaths 准确性 |
| 🟡 P1 | 不完整 | 步骤覆盖面合理但可以更细致，当前版本尚可执行 |
| 🟢 P2 | 措辞润色 | 表述可更清晰，但不影响理解 |
| 🟢 P2 | 格式风格 | 步骤格式、命名风格不一致 |
| 🟢 P2 | 过度拆分 | 步骤拆得过于琐碎，增加了不必要的工作流开销 |

> 与 spec 审查的差异：去除了"方案缺陷"（方案由 spec 决定，plan 不应对此发表意见）；将"上下文断裂"替换为"依赖错误"；新增"粒度不当"。

#### ② 检查重点清单

- 步骤划分粒度是否合理（每个步骤应是独立的可提交单位）
- 步骤依赖顺序是否正确（前置条件是否满足）
- 涉及文件是否完整列出，allowedPaths 是否覆盖所有需要变更的文件
- 是否有步骤同时修改同一文件的不同部分，是否需要合并或拆分
- 每步的验收标准是否可自动/手动验证
- 总的步骤数是否合理（过少意味着粒度太粗，过多意味着过于琐碎）

#### ③ "无问题"判断标准

父 Agent 判断 plan 可以退出循环的标准：

- P0 列表为空（无步骤遗漏、依赖正确、顺序合理、验收标准可衡量）
- P1 列表中无"步骤遗漏"或"依赖错误"类的实质性问题

#### ④ 建议文件命名

- 建议文件：`plan-suggest.md`
- 输出目录：`.harness/temp/{vId}/`

**必须包含以下内容**：

#### ① P0/P1/P2 分类表（代码导向）

| 🟡 P1 | 错误处理不完善 | 网络超时、空值、非法输入等边界错误未处理或处理不当 |
| 🟡 P1 | 性能隐患 | N+1 查询、无必要的重复计算、未使用缓存、大对象未释放 |
| 🟡 P1 | 可维护性 | 逻辑过于复杂、缺少必要注释、不直观的控制流 |
| 🟡 P1 | 测试不充分 | 测试仅覆盖 happy path，未覆盖异常路径或边界条件 |
| 🟢 P2 | 代码风格 | 命名惯例、格式化、导入顺序等风格问题 |
| 🟢 P2 | 重构机会 | 可提取的公共逻辑、可简化的条件表达式（不影响正确性） |
| 🟢 P2 | 过度设计 | 抽象的层级过多、预留的扩展点当前不需要 |

#### ② 检查重点清单

- 实现是否与 spec 规格一致（功能正确性）
- 是否存在安全漏洞（输入校验、认证、数据保护）
- 是否有未处理的错误或异常路径
- 是否引入不必要的依赖或副作用
- 测试是否覆盖核心逻辑和边界条件
- 代码是否可读、可维护
- 是否存在明显的性能问题

#### ③ "无问题"判断标准

父 Agent 判断执行产物可以退出循环的标准：

- P0 列表为空（功能正确、无安全漏洞、不破坏已有功能、核心逻辑有测试覆盖）

## 1. 概述

Review Agent 是一个**独立、挑剔的审查代理**，负责对另一 Agent（Generator）的产出物进行结构化审查。它与 Generator Agent 通过**父 Agent 编排的校验循环**协作，直到产物质量达标或达到最大轮次。

### 1.1 核心协作模式

```
Generator Agent ──产出──→ 产物文件
                              │
Reviewer Agent ──审查──→ 校验建议文件
                              │
                        父 Agent 读取建议，判断是否需要修补
                              │
                    ┌─────────┴─────────┐
                    ▼                    ▼
                需要修补             无需修补
                    │                    │
                    ▼                    ▼
            Generator（修补模式）    退出循环 ✅
                    │
                    ▼
              修改产物文件 → 下一轮审查
```

### 1.2 架构总览

本规格由**一个框架 + 三个场景扩展**构成：

```
┌──────────────────────────────────────────────────┐
│              review.md（本文件）                    │
│  协作模式  │  分级思想  │  校验工作流  │  协作规范   │
└───────┬────────────────────────┬─────────────────┘
        │                        │
        ▼                        ▼
┌───────────────┐   ┌───────────────────────────┐
│  场景扩展文件   │   │    场景扩展文件             │
│               │   │                           │
│ review-spec   │   │ review-plan               │
│ review-exec   │   │ （预留）                    │
└───────────────┘   └───────────────────────────┘
```

| 层次 | 文件 | 职责 |
|------|------|------|
| **框架层** | `.claude/spec/review.md` | 通用协作模式、分级思想、校验工作流、判断标准、协作规范（本文件） |
| **场景扩展** | `references/review-spec.md` | Spec 审查专用的 P0/P1/P2 分类表和检查重点 |
| **场景扩展** | `references/review-plan.md` | Plan 审查专用的 P0/P1/P2 分类表和检查重点 |

## 2. P0/P1/P2 分级评审框架

基于分级的结构化评审方法论，适用于各类文档和产物的审查。

### 2.1 核心理念

1. **分级优先** — 按 P0 > P1 > P2 分级，默认只输出 P0 + P1
2. **范围锁定** — 只审查本次产物，不翻旧账（除非相邻内容暴露了严重问题且修复成本极低）
3. **务实导向** — 考虑修改成本和收益，不追求理论完美

### 2.2 分级定义

三个等级的含义跨场景一致：

| 等级 | 含义 | 父 Agent 动作 |
|------|------|--------------|
| **🔴 P0 — 阻塞级** | 必须修改，否则产物不合格 | 必须进入修补循环 |
| **🟡 P1 — 建议级** | 建议修改，不修改也可接受 | 建议进入修补循环，可人工跳过 |
| **🟢 P2 — 可选级** | 默认不输出，仅润色或风格问题 | 直接退出校验循环 |

### 2.3 通用审查原则

| 原则 | 说明 |
|------|------|
| **范围锁定** | 只审查本次产物的内容。不要质疑产物本身的定位和范围（那是需求阶段的事），只检查产物内的一致性、完整性、可行性 |
| **务实导向** | P0 必须提；P1 选择性提（同类问题出现 3 次以上才提炼为共性问题）；P2 默认不提 |
| **对事不对人** | 语气专业平和，聚焦产物本身的问题，不要用指责性语言 |
| **有据可依** | 每条问题必须有明确依据（内容引用、逻辑推论），不接受"感觉不对" |

> 各等级下具体有哪些类别，由场景扩展文件定义（见 6. 场景扩展架构）。

## 3. AI 校验循环工作流

AI 校验循环由父 Agent 编排，驱动 Reviewer Agent 和 Generator Agent 交替工作。

### 3.1 标准循环流程

```
循环（最多 N 轮）：
  1. 父 Agent 启动 Reviewer Agent（新实例）
  2. Reviewer Agent 读取目标产物文件
  3. Reviewer Agent 生成校验建议 → 写入建议文件
  4. Reviewer Agent 向父 Agent 报告完成
  5. 父 Agent 读取建议文件，判断：
     a. 无问题（或仅轻微措辞建议） → 删除建议文件，退出循环 ✅
     b. 有实质性问题 → 进入第 6 步
  6. 父 Agent 启动 Generator Agent（修补模式），传递建议文件内容
  7. Generator Agent 读取建议文件，逐条采纳建议并修改产物文件
  8. Generator Agent 向父 Agent 报告修补完成
  9. 父 Agent 删除建议文件
  10. 回到第 1 步进行下一轮校验
```

### 3.2 各角色职责

| 角色 | 职责 |
|------|------|
| **Reviewer Agent** | 以独立、挑剔视角审视产物。专注于找出遗漏、矛盾、不清晰之处。输出结构化建议文件给父 Agent，**不直接修改产物文件**。每次都以"第一次审查"的心态重新审视，不因之前提过建议就放行 |
| **Generator Agent（初始模式）** | 负责产物的初始生成。根据需求上下文独立完成，不依赖 Reviewer 的输入 |
| **Generator Agent（修补模式）** | 读取建议文件，逐条评估并采纳合理建议，修改产物文件。**不质疑 Reviewer 的发现**，专注于修补 |
| **父 Agent** | 读取建议文件，判断是否有实质性问题；驱动循环流程；管理临时文件。是"是否继续循环"的唯一决策者 |

### 3.3 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 最大循环轮次 | 5 | 超过后强制退出，产物以当前版本为准 |
| 建议文件后缀 | `-suggest.md` | 如 `spec-suggest.md`、`plan-suggest.md` |
| 是否默认输出 P2 | 否 | P2 级问题默认不输出，除非配置要求 |
| Reviewer 实例策略 | 每次新实例 | 每次循环启动新的 Agent 实例，避免历史偏见 |

## 4. 判断标准

### 4.1 基于 P0/P1/P2 的决策

| 审查结果 | 父 Agent 决策 |
|----------|--------------|
| 有 P0 | **必须**进入修补循环 |
| 仅有 P1，无 P0 | **建议**进入修补循环，但可人工判断是否跳过 |
| 仅有 P2 或无问题 | **直接退出**校验循环 |

### 4.2 "无问题"的判断标准（通用框架）

父 Agent 读取建议文件后，逐条判断：

- **P0 列表为空** — 无阻塞问题
- **P1 列表仅含措辞/格式类建议** — 无实质性问题，可退出循环

> 各场景判断"无问题"的具体标准（哪些算是"实质性问题"）在对应的场景扩展文件中细化。

## 5. 校验建议文件格式

### 5.1 完整报告格式（AI 校验循环用）

```markdown
## 审查结果

### 🔴 P0（N 个）
#序号 [类别] 标题
- **位置**: 章节/段落引用
- **问题**: 具体问题描述
- **依据**: 引用原文或逻辑推论
- **建议**: 具体修改方案

### 🟡 P1（N 个）
#序号 [类别] 标题
- **位置**: 章节/段落引用
- **问题**: 具体问题描述
- **建议**: 具体修改方案

### 🟢 P2（N 个）
#序号 [类别] 标题
- **位置**: 章节/段落引用
- **问题**: 具体问题描述
```

### 5.2 精简版格式（快速判断用）

当只需判断"是否有实质性问题"时：

```markdown
P0: N 个
P1: N 个
P2: N 个

P0 列表：
1. [类别] 标题 — 位置

P1 列表：
1. [类别] 标题 — 位置
```

### 5.3 建议文件生命周期

1. **创建**：Reviewer Agent 写入文件
2. **读取**：父 Agent 读取并判断
3. **传递**：若需修补，父 Agent 将内容传递给 Generator Agent（修补模式）
4. **删除**：每轮循环结束时，父 Agent 删除文件，确保下一轮 Reviewer 不会被旧建议影响

## 6. 场景扩展架构

本框架层不包含场景特定的审查分类表。以下三个扩展文件各自定义对应场景下的 P0/P1/P2 具体类别体系。

### 6.1 扩展文件清单

| 扩展文件 | 审查场景 | 位置 |
|---------|---------|------|
| `review-spec.md` | **Spec 规格文档审查** | `skills/spec-create-harness/references/review-spec.md` |
| `review-plan.md` | **Plan 执行计划审查** | `skills/spec-create-harness/references/review-plan.md` |
| `review-exec.md` | **执行/代码产物审查** | `skills/spec-create-harness/references/review-exec.md` |

### 6.2 各扩展文件的内容约定

每个扩展文件需定义以下内容：

#### P0/P1/P2 分类表

基于自身场景设计专用的类别体系。以下为各场景的框架参考：

**review-spec.md 参考方向（文档导向）：**

| 等级 | 可能的类别 |
|------|-----------|
| 🔴 P0 | 内容遗漏、逻辑矛盾、方案缺陷、不可验证 |
| 🟡 P1 | 描述不清、边界缺失、上下文断裂、不完整 |
| 🟢 P2 | 措辞润色、格式风格、过度设计 |

> Spec 的场景特征：产物是定义性文档，审查重点是完整性和正确性，文档导向的分类天然贴合。

**review-plan.md 参考方向（流程导向）：**

| 等级 | 可能的类别 |
|------|-----------|
| 🔴 P0 | 步骤遗漏、依赖错误（步骤间依赖关系不合理）、逻辑矛盾、不可验证 |
| 🟡 P1 | 描述不清、粒度不当（步骤太大或太小）、文件遗漏、不完整 |
| 🟢 P2 | 措辞润色、格式风格、过度拆分 |

> Plan 的场景特征：产物是执行流程，审查重点在于步骤划分、依赖关系和文件覆盖。去掉"方案缺陷"（翻旧账——方案是 spec 决定的），增加"依赖错误"、"粒度不当"。

**review-exec.md 参考方向（代码导向）：**

| 等级 | 可能的类别 |
|------|-----------|
| 🔴 P0 | 功能不正确、安全漏洞、破坏已有功能、测试缺失 |
| 🟡 P1 | 错误处理不完善、性能隐患、可维护性、测试不充分 |
| 🟢 P2 | 代码风格、重构机会、过度设计 |

> 执行/代码的场景特征：产物是代码变更，审查重点在于正确性、安全性和可维护性。需要一套与文档完全不同的分类体系。

#### 检查重点清单

每个扩展文件应列出 Reviewer Agent 在审查时需要关注的具体检查点，例如：

- **review-spec.md**：功能规格是否完整、技术方案可行性、边界条件覆盖、非功能需求是否明确
- **review-plan.md**：步骤划分合理性、文件依赖顺序、验收标准可验证性、allowedPaths 完整性
- **review-exec.md**：实现与 spec 一致、安全防护、错误处理、测试覆盖、无意外副作用

### 6.3 扩展文件的使用方式

各 skill 的 SKILL.md 在定义审查环节时：

```
1. 引用本框架文件（review.md）获得协作模式和工作流
2. 按场景引用对应的扩展文件获得 P0/P1/P2 分类表
3. 在启动 Reviewer Agent 时，将扩展文件的分类表作为审查标准注入 prompt
```

> ✅ **已实施（2026-07-28）**：`skills/spec-create-harness/SKILL.md` 3.2 和 4.2 节的审查标准已从内联文本替换为引用 `references/review-spec.md` 和 `references/review-plan.md`。启动 prompt 中注入了对应扩展文件的 P0/P1/P2 分类表、检查重点和判断标准。

## 7. 与 Generator 的协作规范

### 7.1 Generator 修补模式行为

| 规则 | 说明 |
|------|------|
| 逐条处理 | 对建议文件中的每条建议逐一评估并处理 |
| 默认采纳 | 除非有充分理由（如建议本身存在事实错误），否则应当采纳 |
| 不质疑 | 不质疑 Reviewer 的发现，专注修补自身产物 |
| 不透支 | 只处理建议文件中明确指出的问题，不擅自做额外优化 |

### 7.2 子 Agent 隔离原则

| 规则 | 说明 |
|------|------|
| 独立实例 | Reviewer 和 Generator 每次循环都用新的 Agent 实例 |
| 不直接交互 | Reviewer 与 Generator 之间不直接通信，所有信息通过父 Agent 协调 |
| 文件为媒 | 产物通过文件传递（产物文件、建议文件），Agent 之间不共享上下文 |
| 视角刷新 | Reviewer 每次以"第一次审查"的心态重新审视产物 |
